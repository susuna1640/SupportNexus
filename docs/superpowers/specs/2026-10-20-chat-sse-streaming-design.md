# 对话 SSE 流式输出设计

## 目的

把 SupportNexus 的聊天交互从“等待所有编排完成后一次性返回”改为“用户能看见请求推进过程和最终回复的文本增量”。用户明确选择默认展示全部可安全公开的过程信息。

现有 `POST /chat` 与其完整 JSON 响应保持不变，确保现有客户端、评测和自动化不受破坏。新增的流式端点由 React 工作台默认使用。

## 用户可见体验

前端在用户消息后立即创建一条空的助手消息和一个过程时间线。服务端依次推送：

1. `status`：请求已接收、正在读取会话记忆、正在识别意图、正在选择 Agent、正在写入记忆。
2. `routing`：安全的路由摘要（意图、主/辅 Agent、置信度和领域分数）。
3. `agent_start` / `agent_end`：每个 Agent 的名称、状态和耗时；并行协作时各 Agent 分别可见。
4. `tool_start` / `tool_end`：工具名称、所属 Agent、成功状态、耗时、缓存/重排标志和简短的公开说明；不发送工具参数、工具返回正文、用户消息、密钥或 Langfuse 采集内容。
5. `delta`：最终面向用户的回复文本片段。单 Agent 的最终无工具生成回合、以及多 Agent 的最终 Response Composer 都应在模型输出时逐段发送。
6. `done`：与现有 `ChatResponse` 字段兼容的完整结果，供前端填充侧栏、请求 ID 与最终 trace；`error`：已公开的阶段和安全错误信息。

前端每接到一个事件就更新同一条助手消息，自动保持在消息底部。过程事件以紧凑、可展开的时间线展示；最终回答仍用现有 Markdown 渲染。用户在一个请求未结束时不能再发起另一条聊天请求，保留当前 UI 的单请求约束。

## API 协议

新增 `POST /chat/stream`，请求体复用 `ChatRequest`。响应为 UTF-8 的 `text/event-stream`，并设置 `Cache-Control: no-cache`、`Connection: keep-alive` 与 `X-Accel-Buffering: no`。每帧使用标准 SSE 格式：

```text
event: delta
data: {"text":"请先确认 "}

```

载荷均为 JSON，序列化时不输出原始工具输入、模型提示词或异常堆栈。连接被客户端取消时，生成器停止、取消仍在运行的编排任务，并且不写入不完整的会话记忆。服务端异常会先发送一个 `error` 事件，再干净结束流；不会伪造 `done`。

Nginx 对 `/api/python/` 的代理关闭响应缓冲，以免中间事件被攒到请求结束才交给浏览器。

## 后端设计

API 层抽出当前 `/chat` 的共享请求生命周期：读取记忆、识别意图、构建 `Request`、编排、写入记忆和构造 `ChatResponse`。普通 `/chat` 调用这个共享逻辑但不注册事件回调；`/chat/stream` 在其异步生成器中注册回调，把生命周期事件编码为 SSE。

编排器、Agent 与工具执行接受可选的异步事件回调。没有回调时保留现有行为和测试契约。路由、Agent 运行、工具运行和 Response Composer 通过回调报告状态。每个请求独立持有回调与工具追踪状态，不能把并发请求的事件混在一起。

Anthropic 兼容客户端的最终文本生成使用其异步流式 API。`content_block_delta` 的文本增量变成 `delta` 事件，同时在服务端累积完整文本，供记忆写入、trace 和最终 `done` 响应使用。工具调用回合先报告工具过程，只有最终面向用户的文本回合才渲染为正式回答；不向用户展示模型内部草稿或推理。多 Agent 请求并行执行各业务 Agent，最后由无工具的 Response Composer 流式生成统一答案；如果 Composer 回退到确定性合并，发送该合并文本作为一个 `delta`。

如果兼容模型端点不支持流式协议，事件流保留过程事件，并将安全完成的一次性最终回复作为一个 `delta` 后发送 `done`；现有非流式 `/chat` 仍可作为兼容入口。

## 前端设计

新增 `requestChatStream`，通过 `fetch` 发起 `POST` 并从 `ReadableStream` 解析 SSE 帧（不用原生 `EventSource`，因为后者不能携带当前的 JSON POST 请求体）。解析器正确处理 UTF-8 分段、跨 chunk 的事件帧、未知事件、HTTP 错误和网络中断。

`sendMessage` 订阅事件并把状态、过程事件、文本和最终结果更新到同一条临时助手消息。收到 `done` 后使用其 `ChatResponse` 填充现有 `lastResponse` 与工具 trace；不再对流式请求额外调用 `/trace/tool/{request_id}`。如果流在完成前失败，保留已经收到的文本和过程时间线，并在该消息中标记错误。

## 非目标与约束

- 不移除或改变 `POST /chat` 的响应结构。
- 不实现浏览器到服务器的双向 WebSocket，也不增加任务队列或持久化的事件回放。
- 不将 LLM chain-of-thought、系统提示词、工具输入、工具原始结果、密钥或原始异常暴露给浏览器。
- 不为未完成或取消的请求写入用户/助手记忆。
- 过程事件是实时 UI 状态，不替代现有可审计的工具 trace 结构。

## 验证

后端测试会验证 SSE 帧格式、事件顺序、完成载荷、错误载荷以及普通 `/chat` 兼容性；Agent 测试会用假流式客户端验证文本累积、工具事件脱敏和 Composer 流式输出。前端构建会验证通过；流解析器将有覆盖跨 chunk JSON/SSE 边界和错误响应的测试（若项目未引入前端测试运行器，则以独立可调用的纯函数测试或构建检查覆盖）。

手动联调会确认：浏览器在回答完成前能看到多个阶段和 `delta`；Nginx 不缓冲事件；单 Agent、有工具、以及多 Agent 编排都在结束时有完整元数据和正确 trace。
